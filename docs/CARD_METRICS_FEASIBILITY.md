# 剧情卡片展示评分与收藏数 可行性报告

> 实测日期：2026-10-26 ｜ 数据源：hongguoduanju.com 公开接口 ｜ 范围：TV 版卡片列表与详情页

## 1. 结论摘要

| 结论 | 说明 |
|---|---|
| 数据本身存在 | 详情页 SSR 下发 `detail_page.seriesSocialInfo`，包含评分、评分人数、收藏数、点赞数、热度；站内搜索接口下发 `favorite_text` / `like_text` / `hot_score_data.text` |
| 全量卡片直接展示不可行 | 首页、分类、题材、榜单、相关推荐的条目数据里都没有评分与收藏字段；要补齐只能按 `series_id` 逐条请求详情页，单页 20~24 条 = 20~24 次额外请求，与「稳定优先、不增加站点并发」的项目约束直接冲突 |
| 未发现批量接口 | 站点前端脚本只引用 `/api/video/protected/`（播放）；实测 6 组候选批量路径全部 404，无按 `series_ids` 批量取社交数据的通道 |
| 可行的落地方案 | 方案 1：搜索结果卡片 + 详情页展示评分与收藏（零新增请求）；全卡片方案（方案 2）建议否决 |

## 2. 实测数据

### 2.1 详情页（唯一稳定来源）

`GET /detail?series_id={id}` → `loaderData.detail_page.seriesSocialInfo`：

| 字段 | 含义 | 实测样例（王妈在顾家当保姆后全家只会搞笑了） |
|---|---|---|
| `rating` | 评分（10 分制，一位小数） | `9.1` |
| `rating_count` | 评分人数 | `37445` |
| `series_favorite_count` | 收藏数（整数字符串） | `2362000` |
| `series_like_count` | 点赞数 | `6147000` |
| `hot_score_data.text` | 热度文本 | `6823万热度` |
| `rank_label` | 榜单标签 | `热播真人剧榜第1名` |

跨类型抽样均取到有效值：

| 类型 | 剧名 | 评分 | 收藏数 | 评分人数 |
|---|---|---|---|---|
| 短剧 | 王妈在顾家当保姆后全家只会搞笑了 | 9.1 | 236.2 万 | 37445 |
| 短剧 | 卖掉养老房那天，我重获新生 | 8.1 | 43.9 万 | 529 |
| 漫剧 | 和离后我带女儿横扫魔域 | 9.0 | 307.7 万 | 10581 |
| 漫剧 | 反派拿捏！第三季 | 9.0 | 68.2 万 | 5578 |
| AI 剧 | 持械入宋：第十季 | 9.0 | 64.7 万 | 12212 |
| AI 剧 | 备用联系人（完） | 9.0 | 179.9 万 | 28651 |

说明：评分分布集中在 8.1~9.1，展示时保留一位小数；`rating` 为 0 或缺失时需回落「暂无评分」。

### 2.2 站内搜索接口（可直接复用的现成字段）

`GET /api/search/result/?query={kw}&page={n}` → `searchList[].video_data`：

```
favorite_text = "318.1万收藏"
like_text     = "416.2万点赞"
hot_score_data.text = "5443万热度"
genre         = "205"
```

字段为已格式化文本，可直接展示，无需自行换算。

### 2.3 无评分/收藏字段的数据源（卡片主体）

| 页面/接口 | 解析位置 | 条目字段 |
|---|---|---|
| 短剧首页 `/category?tab=1&sort_type=1` | `category_page.recommendList` | series_id、series_name、series_cover、episode_cnt、episode_right_text、tags、series_intro、vid_list 等 |
| 漫剧/AI 分类与题材 `/category/...` | `category_$`.`recommendList` | 同上（24 条/页） |
| 榜单 `/rank/rank_hot-*` | `rankList` 序列化载荷 | seriesId、title、cover、description、episodeCount、tags、heatText |
| 详情页相关推荐 | `recommendationGroups.related_list` | 与分类条目一致 |

以上均无 `rating` / `favorite` 类字段，是「全卡片方案」无法回避的硬约束。

### 2.4 批量接口探测

| 探测 | 结果 |
|---|---|
| 页面脚本中出现的 API 路径 | 仅 `/api/video/protected/` |
| `/api/series/social_info/`、`/api/series/social/`、`/api/series/info/`、`/api/series/detail/`、`/api/video/social_info/`、`/api/book/social_info/` | 全部 404 |

## 3. 方案对比

### 方案 1：搜索结果卡片 + 详情页（推荐）

- 搜索结果卡片：展示「收藏 318.1万 · 热度 5443万」，数据来自搜索接口现有字段，零新增请求。
- 详情页：展示「9.1 分（3.7万人评） · 236.2 万收藏 · 6823 万热度」。
- 新增请求：0；新增字段解析：2 处（`search` 的 `card` 映射、`detail` 的 `seriesSocialInfo`）。
- 覆盖范围：搜索页与详情页；首页/分类/榜单卡片维持现状（集数/热度）。

### 方案 2：全卡片展示（否决）

- 每页 20~24 条需逐条请求详情页，单页额外 20~24 次、约 4~5 MB 流量。
- 首屏加载时间显著上升，且与既有「批量请求易触发站点限流」的历史教训冲突。
- 榜单/分类页滚动分页会成倍放大请求量，稳定性风险不可接受。

### 方案 3：本地渐进缓存（不推荐作为主方案）

用户打开过的详情页把评分/收藏写入本地缓存，卡片命中才展示。

- 优点：零新增请求。
- 缺点：覆盖率随时间缓慢增长，同一屏卡片一部分有、一部分没有，视觉不一致；与「收藏/历史」存储耦合，需处理备份解析兼容。
- 定位：只能作为方案 1 的附加优化，不能解决「全卡片」诉求。

### 方案 4：用热度替代收藏（不满足需求）

榜单条目自带 `heatText`，可以零成本把热度放到卡片上，但用户明确要的是评分与收藏数，故不采用。

## 4. 方案 1 的实现要点（若批准）

1. `Series` 增加可选展示字段（默认空串，旧备份反序列化不受影响，且不写入收藏/历史备份 JSON）：
   - `rating: String`（如 `"9.1"`）
   - `meta: String`（如 `"318.1万收藏"`）或分别用 `favoriteText` / `heatText`
2. `ContentRepository.detail()`：解析 `detail_page.seriesSocialInfo`，填充 `Detail` 的评分与收藏展示文本；解析失败静默回落空值，不抛异常。
3. `ContentRepository.search()` 的 `card` 映射：优先取 `favorite_text`，缺失时取 `hot_score_data.text`。
4. 卡片布局：海报下方第二行小字，格式 `9.1 分 · 236.2 万收藏`；宽度不足时只保留收藏数；`rating` 缺失显示「暂无评分」。
5. 焦点与遥控器交互不变，纯文本改动，不新增可聚焦元素。

## 5. 风险与注意事项

| 风险 | 应对 |
|---|---|
| 评分为 0 / 缺失（冷门剧） | 显示「暂无评分」，不显示 0.0 |
| 站点字段改版 | 解析全部走 `runCatching` 静默降级，卡片回落现有集数/热度 |
| 搜索接口被网关拦截时的网站兜底 | 兜底接口同样带 `favorite_text`，两路都能取到 |
| 本地备份体积 | 新字段不写入 `toJson`，备份格式不变 |
| 数字口径 | 直接使用站点返回的「万/亿」文本，避免自行换算产生偏差 |

## 6. 建议

按方案 1 落地：先做搜索结果卡片与详情页的评分/收藏展示，工作量集中在 2 个解析点与 1 处卡片布局；全卡片方案在平台提供批量接口前不实施。
