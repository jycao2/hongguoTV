# 接入其他短剧平台：调研与可行性分析

> 调研时间：2026-10-29　｜　对象：红果TV（Kotlin 原生 TV 客户端，当前 v0.23.0）
> 结论口径：技术可行性、工程成本、可持续性、法律风险四个维度分开评估，不混为一谈。

---

## 一、结论先行

| 路径 | 可行性 | 成本 | 可持续性 | 法律风险 | 建议 |
|---|---|---|---|---|---|
| A. 苹果CMS / TVBox 明文源 | 高（**现有能力已支持**） | 0（加个地址即可） | 低（源随时失效） | 中高 | **就用这条** |
| B. 平台 H5 / 网页版逆向 | 中 | 中（每平台 3-6 人日） | 中低 | **高** | 不建议 |
| C. 平台 App 私有 API 逆向 | 中（技术可复刻） | 高（每平台 5-10 人日 + 长期维护） | 低 | **很高** | **不建议** |
| D. 官方版权合作 / CPS 分销 | 高 | 低（技术）/ 高（商务资质） | 高 | 无 | 个人做不到 |

**一句话结论：** 你真正需要的不是"接入更多平台"，而是"把现有 CMS 通道做扎实"。头部平台没有一条能合法白拿的接口，逆向它们的技术成本接近重做一遍红果，法律成本远高于收益。

## 二、现有架构能承接什么（先划清能力边界）

代码事实（`kotlin-tv/app/src/main/kotlin/com/hongguotv/nativeapp/ThirdCms.kt`）：

- 只实现**苹果CMS v10 明文 JSON 协议**：`ac=list` 分类列表、`ac=detail&ids=` 详情、`ac=detail&wd=` 搜索、`ac=videolist`
- 播放地址按 `$$$` 分组 → `#` 分集 → `名称$地址` 三层解析
- 编码兜底 UTF-8 / GBK，分页按 `pagecount` 或"返回条数 < limit"判尾
- TVBox 配置导入只取 `type=1` 且 api 为 http 的项，**自动跳过 spider jar（type=0）与加密源（type=3/4）**
- 设计文档明确写死：**永久不做 spider jar 动态加载**
- 四层隔离：独立文件、独立 prefs、独立 OkHttpClient、独立 ExoPlayer 实例

**这意味着：** 一个平台能不能"接进来"，取决于它有没有一个明文苹果CMS 接口。有 → 零开发；没有 → 需要新写一整套适配器。

| 河马剧场 | 3853～3919 万 | — | 第二，同比微降 |

### 3.2 技术形态（决定接入难度）

| 平台 | 有 Web 端 | 接口形态 | 能否走现有 CMS 通道 |
|---|---|---|---|
| 红果 | 无独立 Web（App 为主） | 私有 API + 匿名设备注册 + 签名（已完整逆向） | 否，已单独实现 |
| 河马剧场 | **有**（kuaikaw.cn 等） | 网页播放，私有协议 | 否 |
| 喜番 / 星芽 / 繁花 | 多为 App + 小程序 | 私有协议 | 否 |
| 中小影视站 / 短剧聚合站 | 有 | **苹果CMS v10** | **是** |

**关键判断：** 头部平台无一提供苹果CMS 接口。苹果CMS 是自建站程序，云厂商/中小站长才会用；字节、腾讯这类公司不可能把内容挂在 CMS 接口上。

### 3.3 一个反面证据

调研中尝试拉取一个公开的"短剧 TVBox 源"配置（`cnb.cool/fish2018/duanju`），返回：

> **该仓库因 涉嫌资源滥用 已被封禁**

这类源的生命周期普遍只有几个月：先是可用的 CMS 聚合，然后被投诉、封禁、换域名。把它们当作长期内容源不现实——这正是"路径 A 可持续性低"的直接证据。

## 四、四条路径逐一评估

### 路径 A：CMS 源（现有能力，零开发）

**怎么做：** 设置 → 片源 → 添加源/导入配置，粘一个苹果CMS 地址。

**优点：** 已实现、已测、隔离干净；支持多源聚合搜索（`dedupeHits` 已实现跨源去重）。

**缺点（必须承认）：**
- 内容合法性由源站决定，多数是未授权聚合，随时失效
- 画质、集数完整性远不如官方
- 没有弹幕、没有官方更新节奏

**结论：够用就用，不值得为它写一行代码。**

### 路径 B：H5 / 网页版逆向

**适用对象：** 河马剧场这类有 Web 端的平台。

**技术拆解：**
1. 抓网页播放页 → 拿 m3u8 地址 → 看是否带时效签名（多数带 `auth_key` / `expires`）
2. 签名生成逻辑在页面 JS 里，需要还原（可用 Node 侧执行 JS，或移植到 Kotlin）
3. 播放地址常带 Referer / UA 校验，ExoPlayer 侧要注入请求头
4. 登录态 / 付费墙：免费剧可直接看，付费剧需要账号，账号体系不可绕过

**成本估计：** 单平台 3-6 人日（含反爬调试）。**但签名规则一变就要重做**，河马这类平台改版频率以月计。

**法律风险：** 绕过 Referer 校验、还原签名获取真实播放地址，在司法实践中被认定为"技术解析服务"，是 2025 年两高典型案例的打击对象（见第五章）。

### 路径 C：App 私有 API 逆向

**这就是你已经在红果身上做过一遍的事：** 抓包 → 定位签名算法（`libencrypt.so` / DH+AES）→ 设备注册（`ttEncrypt`）→ 风控对抗。

**成本估计：**
- 单个平台首次逆向 5-10 人日（红果你投入了多少，可以自己折算）
- 每个平台一套 native 库、一套签名、一套设备指纹，**不可复用**
- 平台风控升级时要重新对抗（红果 0.21.0、0.23.0 两次大修都是在修"接口集体失效"）

**结论：** 投入产出比最差的一条路。你已经有行业第一的平台，再去逆向第二名，收益是边际内容，成本是复刻整个工程。

### 路径 D：官方授权 / CPS 分销

**这是唯一无法律风险的路径，也是唯一个人做不到的路径。**

行业里已有成熟形态：百川短剧等版权方提供 API/SDK 接入（CPS 分成、CPA 结算、保底+分成），要求合作方具备广播电视节目制作经营许可证等资质；海外侧有 DramaCPS 这类联盟，聚合 ReelShort / DramaBox / GoodShort 等 14+ 平台做 CPS。

**对个人项目的现实：** 需要企业主体、需要签合同、需要走分账结算。一个自家电视用的 APK 不具备条件。

## 五、法律风险（这一章比技术更重要）

### 5.1 判例已经很明确

| 案件 | 事实 | 结果 |
|---|---|---|
| 张某、孙某影视聚合 APP 案（2025 两高典型案例） | 盗链传播 7.2 万余部，广告费 3.92 亿 | 有期徒刑 3 年～5 年 6 个月，罚金 2400 万 |
| 柯某某案（最高检典型案例） | 采集网页播放地址转载到自有网站，广告变现 35 万 | 判 3 年缓 4 年，罚金 40 万 |
| 陆某仟案（(2024)浙0783刑初585号） | 添加视频链接 12 万余部，广告费 148 万 | 判 4 年，罚金 150 万 |
| 短剧专项案（2026 最高检） | 采集 11 万余部微短剧链接，广告变现 | 平台经营者与广告技术方一同判刑 |
| 快手帮助侵权案（2026 二审） | 用户上传侵权短剧，平台未及时处理 | 认定帮助侵权，判令删除、过滤、拦截 |

### 5.2 三个常被误解的点

1. **"我不存视频，只放链接" 不免责。** 法释〔2025〕5 号第十二条明确：使公众可以在选定的时间和地点获得作品，即构成信息网络传播，**不以自有服务器存储为必要条件**。
2. **"我不收费，只放广告" 不免责。** 第二十八条：通过广告费、会员费等方式营利，收取的费用认定为违法所得。柯某某案就是纯广告变现被判刑。
3. **入罪门槛比想象低。** 第十三条：非法经营额 5 万元、传播作品 500 部、点击 10 万次、注册会员 1000 人，任一达标即可入罪；达到十倍进入三年以上量刑档。

### 5.3 个人自用与"运营分发"的分水岭

项目现有免责声明（"仅做技术交流与学习用途，不提供、不存储、不传播任何视频内容"）在**个人自用、不传播、不营利**的前提下是有意义的。一旦出现以下任一情形，这层保护立刻失效：

- 对外分发 APK 并内置源
- 加入任何形式的广告、会员、捐赠入口
- 在公开渠道教人怎么配源

**所以：把源地址写进代码的默认配置、或者发布"开箱即用"的整合包，性质会变。** 现有设计坚持"默认空源、用户自行添加"，这个原则要守住。

## 六、如果一定要接，工程上怎么做

假设你仍然决定接某个平台（比如河马），最小改动方案：

| 步骤 | 内容 | 工作量 |
|---|---|---|
| 1 | 新建 `ThirdCmsHm.kt`，实现与 `ThirdCms` 相同的输出数据类（`ThirdListPage` / `ThirdDetail`） | 1 人日 |
| 2 | 抽象 `ThirdProvider` 接口，`ThirdSourceScreen` 按源类型分发，屏幕上不感知差异 | 0.5 人日 |
| 3 | 实现 H5 签名还原（Kotlin 移植或本地 JS 引擎） | 2-3 人日 |
| 4 | 播放地址注入 Referer / UA（`RemoteVideo` 或独立 OkHttp 拦截器） | 0.5 人日 |
| 5 | 失效检测与降级（签名变了要能明确报错而不是黑屏） | 0.5 人日 |
| 6 | 单测 + 模拟器验收 | 1 人日 |

**关键设计约束（建议写进硬约束）：**
- 新 Provider 必须复用现有四层隔离，不碰红果任何逻辑
- 必须能明确区分"签名失效"与"网络故障"，否则维护时无从下手
- 不做登录态、不做付费内容绕过

## 七、我的建议

**不建议做 B 和 C。** 理由按权重排序：

1. **法律**：这不是"灰色地带"，是有明确判例、有专项打击、有量化入罪门槛的红线。个人自用的边界极窄，一旦分发就是刑事风险。
2. **收益**：红果已是行业第一（2.87 亿 MAU，是第二名的 7 倍）。其他平台的独播内容占比很低，同一批制作方多平台分发，重叠度极高。
3. **成本**：单平台逆向 5-10 人日，且要长期跟风控对抗。你现在维护红果一个平台的接口已经很吃力了（0.21、0.23 两次大修）。

**建议做的事，按性价比排序：**

1. **把 CMS 通道做扎实**（这是唯一可持续的"多平台"能力）：
   - 源健康度历史（现在只有即时探活状态，没有"这个源最近 7 天失败几次"）
   - 单源失效自动降级到备用源（跨源聚合搜索已有，缺自动切换）
   - 播放地址失效时自动换组/换源重试（跟这次做的清晰度自动降档是同一类问题）
2. **不做新平台，做内容覆盖的横向扩展**：红果自身的漫剧、AI 剧分类已接完，边际收益比逆向外部平台高得多。
3. **如果只是想要"更多片源"**：把 `docs/THIRD_SOURCES.md` 里二期规划的"源测速排序"做掉，比接一个新平台有用。
