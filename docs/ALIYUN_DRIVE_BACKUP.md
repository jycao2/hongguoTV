# 阿里云盘云备份与恢复（固定位置）

> 状态：**待评审**（2026-10-23 初版方案；未经用户批准前不改动任何代码）。
> 实施前必须完成「第 9 章 实施前提」的全部验证，任一不通过则终止本方案。

## 1. 目标与范围

在设置页新增**独立入口按钮「云备份（阿里云盘）」**，提供：

- 把本机数据备份上传到阿里云盘的**固定位置**（覆盖式，始终只有一份最新备份）
- 从该固定位置下载备份并恢复到本机

与现有功能的关系：

| 功能 | 存储位置 | 触发方式 | 本方案是否改动 |
| --- | --- | --- | --- |
| 本地备份与恢复 | `/sdcard/hongguotv/` | 启动自动 + 手动 | 不改动 |
| 手机备份与恢复 | 局域网传输 | 手动扫码 | 不改动 |
| **云备份（阿里云盘）** | 阿里云盘应用隔离文件夹 | **仅手动** | **本方案新增** |

明确不做：

- 不做启动自动上传/下载（避免每次冷启动增加外网请求，违背稳定优先原则）
- 不做多份历史版本保留（固定位置固定文件名，始终整体覆盖）
- 不备份首页 7 天缓存等与本地备份一致排除的内容

备份内容完全复用 `LibraryBackup.encode()`（`format="hongguotv.library"`、`version=1`、≤2 MB），数据来自 `LibraryIndex.snapshot()`。云端文件与本地备份文件**字节级同构**，同一份 JSON 既能写 `/sdcard` 也能传阿里云盘，序列化/解码/合并逻辑零新增。

## 2. 云端固定位置定义

| 项 | 值 | 说明 |
| --- | --- | --- |
| 目录 | 开放平台为三方应用分配的**应用隔离文件夹**根目录（用户在云盘「应用/红果TV」下可见） | 三方应用无法访问用户其他目录，天然隔离，用户接受度高 |
| 文件名 | 固定 `hongguotv-backup.json` | 不带时间戳，保证「固定位置」语义 |
| 写入策略 | 存在则覆盖更新，不存在则创建 | 以实际 API 的同名覆盖能力为准（见 5.2） |
| 大小 | ≤ 2 MB（复用 `LibraryBackup.MAX_BYTES`） | 远小于简单上传上限，一次性直传，无需分片 |

## 3. 授权方案（TV 无浏览器的核心难点）

### 3.1 首选：二维码授权 + 轮询

阿里云盘授权体系支持生成授权二维码，手机用阿里云盘 App 扫码确认后，电视侧轮询换取 token（同类三方 TV 客户端的通行做法）：

```
电视                          手机（阿里云盘 App）            阿里云盘开放平台
 │  请求生成授权二维码  ───────────────────────────────►  │
 │◄─────────────  二维码内容（扫码链接 + 会话标识）        │
 │  弹窗显示二维码                                          │
 │                              扫码、确认授权  ────────►  │
 │  轮询授权状态（2s/次）  ────────────────────────────►  │
 │◄─────────────  已确认：authCode                        │
 │  authCode 换 access_token + refresh_token  ──────────►  │
 │◄─────────────  token 对                                │
```

- 二维码弹窗复用现有「手机备份与恢复」的弹窗与 QR 渲染组件
- 轮询上限 3 分钟，关闭弹窗即停止；轮询间隔 2 秒，不触发限流
- **待验证**：该二维码/轮询接口在三方开发者身份下的可用性与稳定性（第 9 章验证项 2）

### 3.2 备选：标准 OAuth + 两步手机操作

若二维码轮询不可用，退化为标准授权码流程：

1. 电视弹窗显示二维码，内容为电视局域网服务页（复用 `LibraryTransferServer` 同构的短时服务）
2. 手机扫码打开页面 → 点「去授权」→ 跳阿里云盘授权页 → 授权完成跳转到**固定静态引导页**（GitHub Pages 等固定地址，创建应用时配置为 redirect_uri），页面醒目显示授权码 + 一键复制
3. 用户回到电视局域网页，粘贴授权码并发送回电视
4. 电视用授权码换 token

缺点：用户多一步复制粘贴；优点：redirect_uri 固定、完全走官方标准流程。

### 3.3 token 管理

| 项 | 设计 |
| --- | --- |
| access_token | 有效期约 2 小时，仅存内存 |
| refresh_token | 持久化在应用**私有目录** SharedPreferences（不进备份 JSON、不进云、不上传任何服务器） |
| 续期 | 每次打开云备份弹窗时用 refresh_token 静默换新 token；refresh_token 随每次刷新轮换，旧值立即作废 |
| 失效处理 | 换 token 失败（用户解绑/令牌过期）→ 弹窗提示「需要重新绑定」，不清除本地任何数据 |

## 4. AppID / AppSecret 的处理（关键安全决策）

阿里云盘开放平台要求应用持有 AppID/AppSecret。本应用为开源 APK，**Secret 内置必然可被反编译提取**，这是该方案最大的妥协点：

- 采用与开源三方客户端一致的惯例：AppID/Secret 以常量内置
- 风险：他人冒用应用身份消耗配额或作恶 → 缓解：配额耗尽仅影响云备份功能，不影响观看主流程；发现滥用可申请吊销重发
- **禁止**因此自建中转服务端（违背项目无服务端架构）
- 实施前在第 9 章确认平台是否提供免 Secret 的纯客户端模式（PKCE），若提供则优先采用

## 5. 核心流程

### 5.1 恢复（下载）

```
打开弹窗 → 静默刷新 token → 定位固定文件（应用文件夹内按文件名查） 
  → 获取临时下载地址 → 下载 → LibraryBackup.decode（容错解码）
  → 电视弹确认框 → LibraryBackup.merge（复用现有合并语义）→ 落盘 → Toast 结果
```

- 未找到固定文件：提示「云端还没有备份」，不报错
- 下载内容损坏/格式非法：复用容错解码，失败提示「云端备份已损坏，本地数据未改动」
- **永远先解码成功再弹确认框**，用户确认前不触碰本地数据（与手机恢复同一原则）

### 5.2 备份（上传）

```
LibraryIndex.snapshot() → LibraryBackup.encode 
  → 查固定文件：存在 → 覆盖更新其内容；不存在 → 在应用文件夹创建
  → Toast「云端备份已更新」
```

- 覆盖优先使用 API 的同名覆盖/内容更新能力；若平台不支持原地更新，采用「上传临时文件 → 删除旧文件 → 改名」三步，任一步失败云端仍保留旧备份（与本地轮换写同思路）
- 上传失败：Toast 提示失败原因（网络/配额/授权失效），本地数据无影响

### 5.3 恢复时的合并语义

完全复用 `LibraryBackup.merge(local, incoming, replace)`：

- 默认走合并（收藏去重、进度取 `updatedAt` 较新者）
- 弹确认框时提供两个按钮：**合并恢复**（默认焦点）/ **覆盖本机**（二次确认）

## 6. UI 设计

设置页新增独立按钮，位置在「手机备份与恢复」之后：

| 状态 | 按钮文案 |
| --- | --- |
| 未绑定 | `云备份（阿里云盘）  ·  未绑定` |
| 已绑定 | `云备份（阿里云盘）  ·  已绑定` |
| 刷新失效 | `云备份（阿里云盘）  ·  需重新绑定` |

点击后弹窗（复用 `TvDialog` 视觉规范）：

- 未绑定：说明文案（数据直连阿里云盘、不经任何中转、只访问独立应用文件夹）+「扫码绑定」按钮 → 二维码弹窗（3.1）
- 已绑定：选项列表「立即备份到云端 / 从云端恢复 / 解除绑定」
  - 解除绑定：二次确认，仅删除本地保存的 refresh_token，云端备份文件保留

焦点规则沿用设置页现有规范：弹窗打开默认焦点在首个操作按钮，关闭后焦点回到设置项按钮本身。

| 层 | 新增/改动 | 内容 |

| core | **新增** `AliyunDriveBackup.kt` | OAuth 换 token/刷新、固定文件查/建/覆盖/下载；独立 `OkHttpClient`（connect 8s / read 30s），不进 `Http` 拦截器白名单体系，与红果接口零关系 |

不新增对红果站点的任何请求，不增加站点并发；所有云请求直连 `openapi.alipan.com`。

## 8. 隐私与合规

- README 免责声明追加一条：「云备份功能为用户主动触发的个人数据迁移，数据在用户自己的阿里云盘账户内传输与存储，本应用不经过、不收集任何中转服务器」
- refresh_token 不出设备；备份 JSON 与本地备份同为明文（云盘内用户自行负责）

## 9. 实施前提（全部通过才动工）

1. **开发者申请**：在阿里云盘开放平台注册三方开发者、创建应用拿到 AppID/Secret 通过审核（个人项目存在审批不通过的可能，此为最大前置风险）
2. **二维码授权验证**：实测 3.1 的二维码生成 + 轮询接口在三方身份下可用；不可用则确认 3.2 备选落地
3. **PKCE/免 Secret 模式确认**：若平台支持纯客户端模式则采用，规避第 4 章风险
4. **隔离目录与覆盖写入验证**：实测三方应用在隔离文件夹内创建/同名覆盖/下载的完整链路
5. 以上 4 项任何一项不通过：方案终止，退守现有本地备份 + 手机迁移
