# 取流封禁的“永久方案”调研（2026-11-23）

> 触发：19:50 起 App 取流全线 `HTTP 200 + 0 字节`，持续 1.5h 未恢复。
> 疑问：“有没有能永久解决的方案？”
> 结论先说：**没有永久方案**；但有 3 家独立跑通的配方，且恢复期必须“停手 1~2 天”。

## 一、为什么不存在永久方案

1. **这是商业限制，不是反爬 bug。** 官方对匿名设备“只给一次播放模型”（openhongguo 文档明写，自 2026-10-29 起），目的是“不付费不能看全集”。
2. **签名族两个月换 4 代**：7.1.3.32 → 7.3.5.32 → 7.3.9.32 → 7.4.3.32 → 7.4.5.32。依赖签名的通道，永久性为零。
3. **决定性反证**：官方自己的 CLI（openhongguo v0.4.0）+ 连续两台全新设备 + 正确参数 = `anonymous response was empty`。封禁来自平台侧，不是客户端 bug。

### 关键行为差异（不是字段，是策略）

- **不要在同一身份上做递增退避等待**（真果鉴 0.8.27：旧逻辑 0.8/1.4/2.0/2.5s 递增，p50 12.49s 全在空等）。
- **不要在空响应后反复重注册**（同行 0.27.4：“空响应时先尝试备用身份，避免反复重注册”）。
- **403 只当签名失配、就地换签名重试；只有真 429 才停手**（真果鉴）。
- **device_level 升档状态要保留**（同行：4 → 5 之后保留 5，不清回 4）。

## 三、最要紧的一条：恢复期是 1~2 天，不是 1 小时

`POf-L/Fanqie-novel-Downloader#483` 作者原文：

> 也请不要再手动回拨 last_rotated_at：**72 小时一次是故意的上限**，短时间里反复换号、反复请求，只会让风控更难解除。**建议先停一两天再试。**

对照我们的历史：第一次触发约 49 秒恢复，第二次 >10 分钟，这次 >1.5 小时——**恢复时间随触发次数递增**，与“触发越多越难解除”完全吻合。

**行动纪律**：窗口未开期间，任何“再试一次看看”都会延长封禁。要么等，要么走下面的备用通道。

## 四、备用通道：官网 Web 接口（与 App 风控完全独立）

2026-11-23 21:23 实测：**App 接口全封的同一时刻，官网接口正常出地址**。两条链路风控独立。

| 接口 | 方法 | 需要签名 | 覆盖 | 清晰度 | 有效期 |
|---|---|---|---|---|---|
| `/api/video/protected/fallback-play-info?aid=8662` | POST | 否（`x-xs-from-web: 1` + Referer） | 每剧前 3~5 集 | 360P mp4 | ~1h |
| `/api/video/protected/play-info?aid=8662` | POST | 否（同上） | 每剧**前 3 集** | **720P h264 DASH** | ~1h |

请求形态：

```http
POST https://hongguoduanju.com/api/video/protected/play-info?aid=8662
Content-Type: application/json
x-xs-from-web: 1
Referer: https://hongguoduanju.com/player/<series_id>

{"series_id":"<剧级id>","item_id":"<集vid>","definition":"720p"}
```

响应 `play_info`：`main_url` / `backup_url` / `player_access_key` / `format=dash` / `codec_type=h264` / `expires_at`。

**边界实测**（2026-11-23 21:25，《萌娃助攻》85 集）：
- 第 1/2/3 集 → 720P OK
- 第 4 集起 → `{"error":"protected_playback_unavailable"}`
- 1080p / 540p → 无 `play_info`；只有 720p / 480p / 360p 有货
- 第 6 集用官网登录 Cookie 是否解锁：**未验证**

**价值**：App 通道死掉时，用户至少能看每部剧前 3 集 720P，消灭“一打开就什么都看不了”。但要全集仍无解。

## 五、还有一条活着的 App 接口：`video_detail`

`/novel/player/video_detail/v1/`（POST JSON，要 App 签名）在 21:25 仍 `code=0`，返回整部剧的 `video_list`（85 集的 vid/时长/封面）。

- **要的是 `series_id`（剧级 id），不是单集 vid**；传 vid 回 `100001 series_id invalid`。
- 只返回元数据，**不含任何 mp4/m3u8/play_url**，所以它是详情接口不是取流入口。
- 用途：拿到全部分集 vid，喂给官网 `play-info` 逐集试。

## 六、结论与优先级

1. **先停手 1~2 天**（最高优先级）。这期间不要再打 App 取流接口。
2. 本次已对齐两处关键字段（`device_level=4` + 删 PLAYER `dr_scene`），等窗口开验证。
3. 若恢复后仍全空，下一个怀疑对象是 **Medusa 新版算法**（我们的 `medusaV5` 是 v04.10.03 支，同行已换 HGTV 1.3.8.1 支）。
4. 中期做官网 `play-info` 兜底（前 3 集 720P），让“App 全封”不等于“什么都看不了”。
5. 长期唯一解是**用户自己的账号**（短信登录已打通，登录态能否放行取流**待窗口开验证**）。

## 七、教训（写给自己）

- 不要靠“升版本号/换设备”盲试——6.9.1.32 ~ 7.4.6.32 全试过全空。
- 不要照抄上游抓包里的单个字段就加进去：`dr_scene="player"` 就是这么错的（openhongguo 是 PRELOAD 场景）。
- 判断“是不是我们的锅”最快的方法：跑官方 CLI。它都空，就不是我们的问题。
